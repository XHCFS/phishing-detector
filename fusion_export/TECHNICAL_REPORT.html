1. Architecture Overview

The fusion detector scores every URL through two independent models whose outputs are averaged into a single deployment probability. A threshold of 0.35 determines the verdict. An optional content gate handles gray-zone commerce and platform phishing when full enrichment is available.

1
URL NORMALISATION — canonicalize_url_batch() inside the joblib pipeline via FunctionTransformer. HTTP→HTTPS upgrade, lowercase, strip trailing slash. No manual call needed at inference time.
2
URL CHAR LR — Character n-gram (2–4) logistic regression over hashed features (218 buckets). Scores URL surface patterns only. No network calls. Returns url_p ∈ [0,1].
3
LIVE ENRICHMENT — WHOIS (domain age, registrar, expiry), GeoIP/ASN (MaxMind mmdb), TLS certificate (issuer, validity), HTTP (status code, page title, language, form action, favicon, password fields). Results cached per URL. Latency: 2–8 s per URL on cold cache.
4
HGB OPERATIONAL — HistGradientBoosting classifier on 44 enriched features (raw + derived). Scores hosting infrastructure independently of URL surface patterns. Returns op_p ∈ [0,1].
5
FUSION — deploy_p = mean(url_p, op_p). Threshold: 0.35. Benign ceiling (cdn.jsdelivr.net): 0.261. Safety margin: 0.089.
6
CONTENT GATE (optional, --content-gate) — Fires when deploy_p ∈ [0.08, 0.35) or commerce keywords in hostname. Fetches HTML, checks 5 signals: brand impersonation, credential harvest offsite, cart-without-trust, discount density, copyright mismatch. Boost weight 0.45.

3.3 Ephemeral Platform Feature — Design & Calibration

Problem addressed: Phishing kits hosted on legitimate SaaS platforms (GitHub Pages, Adobe Portfolio, Square Sites, Vercel) produce clean operational features — the ASN, domain age, and TLS cert belong to the platform, not the attacker. Prior to v1.9.0, the operational model had no signal for this attack class.

21 platform suffixes detected: vercel.app, pages.dev, github.io, netlify.app, web.app, glitch.me, webflow.io, fly.dev, render.com, railway.app, surge.sh, usercontent.dev, myportfolio.com, company.site, squarespace.com, weebly.com, wixsite.com, cargo.site, notion.site, blogger.com, blogspot.com.

Calibration requirement: Without training examples of legitimate ephemeral-platform sites, HGB treated is_ephemeral_platform=1 as near-deterministic phishing (FPR on benign_platform_legit jumped from 6.7% to 100%). Fix: 1,500 synthetic calibration rows injected into training — 500 benign developer portfolios (no brand name, neutral title, old platform apex domain) + 500 phishing platform impersonation rows (brand in subdomain, brand in title, fresh domain age) + 500 legitimate brand SSO pages (old domain, current cert, Microsoft/Google/Apple ASN, login keywords but brand matches domain).

The HGB model learns: is_ephemeral_platform=1 + subdomain_brand_count=0 + title_has_login_kw=0 → low op_p and is_ephemeral_platform=1 + subdomain_brand_count≥1 + title_brand_mismatch=1 → high op_p.

7. Known Limitations & Failure Modes

#Failure ModeEstimated Miss RateRoot CauseMitigation
L1 Platform phishing (no brand name) ~50–80% Attacker uses personal-sounding subdomain (toddb007, store123) on legitimate SaaS (Adobe Portfolio, Square Sites). Both models see clean infrastructure. Content gate (--content-gate). Page fingerprinting. DOM analysis.
L2 OAuth redirect injection ~100% Attacker embeds phishing URL in redirect_uri param of legitimate OAuth host. Model scores on surface URL (accounts.google.com) → benign. Parameter extraction + recursive scoring of redirect_uri target.
L3 Opaque URL shorteners Resolved (v1.9.1) Production pipeline follows 3xx redirects via resolve_short_url() before enrichment. Benchmark FPR was 100% (scored opaque code, not destination). Fixed with: (1) shortener-aware fusion weighting (10% url_p / 90% op_p for unresolved shorteners) + (2) 200 diverse code augmentation + (3) 400 synthetic HGB calibration rows for old trusted shortener domains. Resolved. Benchmark FPR=0% all seeds. Production always resolves before scoring. Defense-in-depth via shortener fusion for rare resolution failures.
L4 Dead / stale phishing links Inverse — FP risk Phishing domain with suspicious URL pattern still scores high even after domain expires. Add feed recency signal (last_seen days) as operational feature.
L5 European personal-name ccTLD domains Low — FP risk profil.monxtra.be — "profil" matches phishing subdomain keywords; .be ccTLD unfamiliar to model. Expand European ccTLD benign anchors in augment_hard_benign.txt.

8. Comparison: v1 Rule-Based vs v1.9.0 Fusion

The prior system (v1.1, October 2025) used five hand-coded rule components scoring 0–100. Known critical weakness: long tracking URLs with hash tokens accumulated keyword + length + TLD points and were falsely flagged as phishing.

FPR (real-world)~2% (claimed on Alexa top-1000; not enterprise email URLs)2.4% (measured on 250 live enterprise/consumer URLs)

8.1 Integrations from v1 into v1.9.0 (completed)

  • Ephemeral platform TLD signal — v1 explicitly penalised .vercel.app, .pages.dev, .github.io. Now implemented as is_ephemeral_platform operational feature.
  • MAX aggregation pattern — v1 email risk = MAX(all URL scores). The /score endpoint accepts up to 500 URLs; caller takes max of deploy_p values for email verdict.

8.2 Recommended Future Integrations from v1

  • Feed recency signal — v1 down-scored URLs with stale last_seen timestamps. Add feed_recency_days as operational feature to penalise dead phishing domains.
  • STIX 2.1 export — v1 emitted STIX Indicator bundles. Useful for SIEM integration.
  • Campaign clustering — v1 mentioned DBSCAN on ASN/registrar/nameserver triplets. v1.9.0 enriched features support this.

13. Answers to Key Questions

QuestionAnswer (v1.9.0)
What is the real-world TPR?~93% on fresh PhishTank URLs (90–100% across samples). 99.33% on OpenPhish credential phishing kits specifically.
What is the real-world FPR?~2.4% on diverse enterprise/consumer benign URLs. 0% on the OpenPhish benchmark's 60 benign URLs (underestimated production FPR).
What attack class is most evaded?Platform phishing without brand name (toddb007.myportfolio.com). Requires content gate.
Why not just use the URL model?URL model alone: ~60–75% TPR on email traffic (hash tracking URLs cause FPs; platform phishing evades). Dual fusion: 93% TPR with 2.4% FPR.
Is this better than v1 rule-based?Yes. v1 failed systematically on long hash URLs (FP) and any attack without explicit keywords. v1.9.0 is immune to hash URL FPs and generalises to unseen attack patterns.
Can it handle email?Yes, via URL extraction + MAX aggregation. See §9.2. FPR on tracking URLs in email body is <1%.
How fast is it?URL scoring: microseconds. Full enrichment (cold): 2–8 s/URL. HTTP sidecar: 500 URLs/batch. Cache warm: <100 ms/URL.
